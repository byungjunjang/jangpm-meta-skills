# Agent Design Questions (Blueprint 심화 전용)

`/blueprint`로 만든 에이전트 설계 초안을 심화할 때 쓰는 질문 축. `question-library.md`가 일반 스펙용이라면 이 파일은 **이미 blueprint 문서가 있다는 전제**로, 그 문서의 빈틈·암묵 전제·설계 결정의 근거를 찔러 보는 forcing 질문들이다.

SKILL.md의 Phase 3(Forcing Interview)에서 심화 모드일 때 `question-library.md`와 병행해서 로드한다.

사용 규칙은 `question-library.md`와 동일. 단, 여기서는 "blueprint 문서에 무엇이 적혀 있는지"를 먼저 확인하고 그 내용을 질문에 인용(quote)해서 사용자가 자기 문서를 다시 보게 만든다.

---

## A. Trigger / 입력 신호

### A-1. 트리거 조건의 완결성
- **Q**: "blueprint에 적힌 트리거 조건이 `[blueprint에서 인용]` 인데, 이 조건만으로는 안 걸리는 엣지 케이스가 뭐가 있나요?"
- **Push for**: 걸리지 않을 케이스 하나 이상 + 그걸 어떻게 처리할지 (의도적 제외 / 별도 트리거 추가 / 수동 실행)
- **Red flags**: "다 커버돼요", "모든 경우에 걸릴 거예요"
- **Follow-up**: "예를 들어 입력이 일부만 맞는 형태로 들어오면 어떻게 되죠? 아예 안 돌아가나요, 잘못된 답을 내나요?"

### A-2. 신호의 신뢰도
- **Q**: "트리거 신호가 오는 쪽(n8n, webhook, 파일 변화, 사용자 명령 등)이 실패하거나 중복되면 어떻게 되나요? blueprint 어디에 그 대응이 적혀 있나요?"
- **Push for**: 중복/누락/지연 시 동작 명시 + 책임 경계 (트리거 측 책임 vs 에이전트 측 책임)
- **Red flags**: "그쪽에서 안 실패할 거예요", "알아서 처리"
- **Follow-up**: "같은 트리거가 2번 연속으로 오면 이 에이전트는 2번 돌아야 하나요, 1번만 돌아야 하나요? idempotent한가요?"

## B. LLM vs 코드 경계

### B-1. LLM으로 잡힌 단계의 타당성
- **Q**: "blueprint에서 LLM 호출로 처리하는 단계 중 `[단계 이름 인용]`가 있는데, 이 단계는 왜 코드로 안 되고 LLM이 필요한가요?"
- **Push for**: LLM이 해결하는 '판단/해석/생성' 요소 명시 + 코드로는 왜 못 하는지
- **Red flags**: "그냥 LLM이 편해서", "코드 짜기 번거로워서"
- **Follow-up**: "이 단계의 입력과 출력이 정형화돼 있다면 정규식·룰 기반 코드가 더 싸고 안정적입니다. LLM이 꼭 필요한 부분만 남기고 나머지를 코드로 뺄 수 있을까요?"

### B-2. 코드로 잡힌 단계에 숨은 판단
- **Q**: "blueprint에서 코드(스크립트·도구)로 처리한 단계 중 사실 사람의 판단이나 문맥 해석이 필요한 곳이 있나요?"
- **Push for**: 구체적 코드 단계 한 곳 + 거기 판단 필요한 이유
- **Red flags**: "전부 룰 기반으로 충분", "그건 절대 실패 안 함"
- **Follow-up**: "입력이 예상과 다른 포맷으로 들어오면 그 코드는 어떻게 되나요? 실패? 잘못된 결과? 그때 누가 잡나요?"

## C. 서브에이전트 구조

### C-1. 단일 vs 병렬의 근거
- **Q**: "blueprint가 `[단일 세션 / 병렬 서브에이전트]`로 가는데, 이 선택의 근거가 뭔가요? 반대 구조였다면 뭐가 안 되나요?"
- **Push for**: 선택 근거 + 반대 구조에서 발생할 구체적 문제
- **Red flags**: "그냥 이쪽이 자연스러워서", "예전에 해본 게 이 방식이라"
- **Follow-up**: "서브에이전트 간에 공유할 상태가 있나요? 있으면 병렬이 복잡해지고 없으면 순차가 낭비입니다. 어느 쪽인가요?"

### C-2. 컨텍스트 사이즈
- **Q**: "각 에이전트가 한 번에 다루는 입력·문서의 크기가 어느 정도인가요? 컨텍스트 한계에 걸리는 시나리오가 있나요?"
- **Push for**: 대략적 토큰·파일 수 + 한계 시나리오
- **Red flags**: "작아서 괜찮아요", "요즘 모델은 커서 상관없음"
- **Follow-up**: "최악의 경우(가장 큰 입력)를 상상했을 때 몇 kB, 몇 파일인가요? 그 케이스에서도 한 세션에 다 들어가나요?"

## D. 실패·환각 처리

### D-1. 환각 검출 지점
- **Q**: "LLM이 그럴듯한 거짓말을 했을 때 blueprint의 어느 단계가 그걸 잡나요? 검증 로직이 있나요?"
- **Push for**: 구체적 검증 단계 (파일 존재 확인, API 응답 스키마, 서브에이전트 리뷰 등)
- **Red flags**: "모델이 잘 안 틀려요", "프롬프트를 잘 써서 방지"
- **Follow-up**: "프롬프트로는 100% 막을 수 없습니다. 실행 후 결과를 기계적으로 검증하는 지점이 하나는 필요해요. 어디에 둘까요?"

### D-2. 재시도 전략
- **Q**: "LLM 호출이나 도구 호출이 실패했을 때 blueprint가 어떻게 대응하나요? 재시도? 다른 경로? 사용자에게 위임?"
- **Push for**: 실패 유형별 전략 (일시적 네트워크 / 영구적 오답 / 부분 성공)
- **Red flags**: "알아서 재시도", "에러 뜨면 멈춤"
- **Follow-up**: "같은 호출을 3번 돌려도 같은 실패가 나올 때와 그렇지 않을 때 대응이 달라야 합니다. 두 경우를 구분하고 있나요?"

## E. 산출물 검증

### E-1. '맞다'의 정의
- **Q**: "이 에이전트의 산출물이 '맞다/틀리다'를 어떻게 기계적으로 판단하나요? blueprint에 그 기준이 적혀 있나요?"
- **Push for**: 검증 가능한 기준 (스키마 / 정규식 / 테스트 / 사람 승인 중 하나)
- **Red flags**: "보면 알아요", "대충 맞으면 됨"
- **Follow-up**: "한 달 뒤 에이전트 돌린 결과 1000개 중 '틀린' 것만 뽑는다면, 무슨 기준으로 뽑나요?"

### E-2. 검증 단계의 위치
- **Q**: "blueprint에 검증 단계가 있다면, 그게 파이프라인의 어느 지점에 있나요? 왜 거기인가요? 더 앞에서 잡을 수는 없나요?"
- **Push for**: 검증 위치 명시 + 위치 선택 근거 + 앞당기기 가능성 검토
- **Red flags**: "맨 마지막에 한 번", "단계마다 일단 다 통과"
- **Follow-up**: "검증을 앞쪽으로 옮기면 실패를 싸게 잡지만 느려집니다. 뒤로 옮기면 빠르지만 비싸게 발견합니다. 이 에이전트는 어느 쪽이 맞나요?"

## F. 인간 개입점

### F-1. 체크포인트의 필요성
- **Q**: "blueprint 어느 지점에서 사용자가 '잠깐, 여기서 확인할게'라고 끊어야 하나요? 지금 blueprint의 체크포인트가 실제로 필요한 지점에 있나요?"
- **Push for**: 체크포인트 위치 + 그곳이어야 하는 이유 (되돌리기 비용이 큰 직전, 방향 결정 지점 등)
- **Red flags**: "사용자가 끼어들 필요 없음", "맨 끝에서만 보면 됨"
- **Follow-up**: "끝까지 돌아간 뒤 결과가 방향부터 틀렸다면 얼마나 낭비되나요? 그 비용이 크다면 중간에 체크포인트가 필요합니다."

### F-2. 과도한 개입
- **Q**: "반대로, blueprint에 체크포인트가 너무 많아서 사용자가 귀찮아할 지점은 없나요? 자동화의 의미가 희석되는 곳이요."
- **Push for**: 지나친 확인을 제거할 수 있는 지점 + 자동화 가능 근거
- **Red flags**: "확인은 많을수록 좋죠", "체크포인트 없애기 무서워요"
- **Follow-up**: "사용자가 이 에이전트를 하루에 10번 돌린다면 그때도 매번 같은 확인을 받으실 건가요? 어떤 체크포인트를 '한 번 허락하면 계속 허락'으로 전환할 수 있나요?"

## G. Blueprint 자체의 전제

### G-1. 문서의 암묵 전제
- **Q**: "blueprint를 지금 다시 읽어봤을 때, 문서에 쓰여 있지 않지만 '이게 참이어야 돌아간다'고 깔려 있는 전제 2–3개는 뭐라고 보시나요?"
- **Push for**: 비명시 전제 2–3개를 명시 + 각 전제가 깨질 신호
- **Red flags**: "모두 명시돼 있어요"
- **Follow-up**: "명시된 것만으로는 설계가 성립하지 않습니다. 예를 들어 '사용자가 한국어를 쓴다', '입력 파일이 1MB 이하다' 같은 것들이 깔려 있어요. 이 설계의 경우 무엇이 있나요?"

### G-2. 초기 설계 결정 재검토
- **Q**: "blueprint 맨 처음에 내린 구조적 결정 중, 지금 다시 고른다면 바꿀 법한 게 있나요?"
- **Push for**: 구체적 결정 하나 + 바꿀 이유 OR "지금 봐도 이 이유로 그대로"
- **Red flags**: "다 맘에 들어요"
- **Follow-up**: "모든 결정이 완벽해 보이는 건 보통 도전받아 보지 않았을 때의 신호예요. 가장 덜 확신이 가는 결정 하나만 짚어주세요."
